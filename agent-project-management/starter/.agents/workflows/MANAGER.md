# Manager Workflow

Use the local project-control policies and approved task boundaries. Keep this procedure independent of model brands and harness features.

## Resume and choose the next action

1. Inspect repository status, branch, current default-branch commit, active workers, and owner-local preservation rules.
2. Read the handoff, active task, and any campaign state. Reconcile evidence newer than the handoff before assigning work.
3. Read the relevant SPEC, adopted decision, PRD requirement, and cited source. Resolve material disagreement rather than assuming a linear document ranking makes it disappear.
4. Identify the active dependency-return chain and the next action already authorized. Routine in-scope work continues without another permission request.

## Prepare and dispatch

Choose the task mode. A research or packet task stops at its named artifact/review gate. An implementation task needs a defined behavior, scope, proof, release boundary, and the relevant adopted decisions.

For a material unresolved choice, produce a concrete decision request with source evidence, recommended option, alternatives, consequences, and the exact blocked task. Record actual adoption before revising the governing plan or implementing it. Avoid making the owner decide routine code organization within an approved design.

Populate one card and one complete launch prompt. Establish the baseline, suitable isolated checkout, packet presence, allowed files, environment, test expectations, and final report. State commit/push/release authorization. Concurrent workers need separate checkouts and declared ownership; authorize delegation deliberately according to the local policy.

## Review the result

- Inspect the delivered diff and important test evidence, including producer/consumer composition and failure paths.
- Check scope, new authority, data consequences, safe diagnostics, and the meaning of predecessor-test edits.
- Verify baseline comparisons and distinguish source, fixture, integration, and owner evidence.
- Resolve each finding: focused correction, accepted task, decision, explicit deferral, or supported rejection.
- Confirm the worker collected pending commands and completed the approved goal. A report alone does not prove delivery.

## Release and reconcile

Apply the project's release and approval policy. Verify the merge/release revision and synchronize only through safe operations that preserve local work. Package a precise owner test when required: build/restart instructions, prerequisites, one bounded action, expected observations, retained evidence, and stop conditions.

Record acceptance separately from merge. Update the handoff when state or sequencing changes, route cross-task findings into the register, and follow return links back to blocked parents. Before closeout, check outstanding decisions, acceptance gates, and deferred work that could block the next phase.

## Keep continuity small

The handoff owns current program state; the task owns scope and proof; the decision log owns adopted rationale; SPEC owns implementation. Link these rather than repeating their contents. Archive old operating briefs at major boundaries. Record framework improvements as proposals with examples and upgrade impact.
