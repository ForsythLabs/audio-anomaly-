# Worker Workflow

Complete one approved task through its stated delivery boundary. The task card and project profile determine whether the goal is research, packet preparation, implementation, or review.

## Intake

Confirm the actual checkout, branch, baseline ancestry, packet revision and approval, relevant decisions, allowed paths, installed tools, and preservation rules. Read the relevant SPEC and source. Report a material mismatch before dependent edits; do not reset or rename a checkout simply to satisfy stale text.

Maintain a short checklist of required artifacts, proof, regressions, documentation, and commit/push state. The checklist tracks the current goal; it does not authorize later goals.

## Perform the task

For research and packet work, gather the evidence needed for the named question, label hypotheses, and stop at the artifact/review gate. Do not treat a coherent proposal as approval to implement.

For implementation:

1. Establish the relevant untouched baseline before edits; use a separate pristine checkout if the run must overlap implementation.
2. Add meaningful failing coverage for the behavior, with a delivering control when refusal-only fixtures could mislead.
3. Implement the smallest coherent change within the approved module boundary. Prefer reusable authority and contracts over a parallel path that will need replacement.
4. Execute focused and required regression checks. Inspect stderr and investigate failures; do not repeatedly retry or weaken an assertion to obtain green.
5. Exercise the production producer/consumer boundary when substitutes could conceal contract drift. Name every important substitute and proof limit.
6. Update allowed SPEC sections after behavior is verified, and record scope deviations and pending acceptance in the task evidence.

Documentation-only work needs appropriate document checks; do not invent a failing product test. A late-added verifier may use a discriminating mutation while reporting that it was written after the correction.

## Handle discoveries and interruptions

Resolve routine in-scope choices independently. If progress needs changed authority, material scope expansion, a missing governing decision, or an action reserved by local policy, finish independent authorized work and report the concrete blocked action with evidence and bounded alternatives.

Record unrelated findings in the closeout for management triage. Do not edit manager-owned plan state, handoff, follow-up register, or approval records unless the task assigns that role.

After a context reset or limit, re-read the card, state, Git status and pending process results, then continue the same goal. Preserve partial changes and original error evidence. If a checkout is missing, inspect the surviving branch and worktree metadata before proposing recovery; never claim uncommitted work survived without evidence.

For a model safeguard refusal, preserve the checkpoint and report the category when available. Follow the reviewed handoff process rather than rephrasing to bypass the refusal or silently switching models.

## Deliver

Collect pending tests or agents before claiming completion. Stage exact task paths. Commit and push only as authorized by the card and project policy; follow its stop/review boundary. Report the commit/branch, changed behavior, RED/GREEN or applicable document evidence, regressions, limits, remaining owner acceptance, deviations, and decisions needed. Do not self-approve a release or start the next task.
