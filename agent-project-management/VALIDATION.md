## Author desk checks

| Scenario | Expected next action from the supplied records |
| --- | --- |
| Empty project with only an idea | Establish requirements and local policies; record no implementation only after inspection; propose a bounded first task. |
| Existing project already has different PRD/SPEC paths | Map and reuse the existing records in project control; avoid competing documents and replacement of local rules. |
| Newer source contradicts an old SPEC or handoff | Establish the discrepancy, reconcile current evidence, and assess task impact before dispatch. Do not silently rewrite an adopted requirement. |
| Worker finds a new architectural prerequisite | Preserve the parent as blocked, prepare the decision and bounded dependency, record its return link and release evidence. |
| Focused refusal tests pass but the real producer returns a different shape | Exercise the real producer/consumer composition and add a success control; do not treat the stub's green result as integration proof. |
| Test suite is running while edits begin | Use an untouched separate checkout or finish the baseline first; do not retain a mixed-source run as baseline. |
| Work is pushed but unmerged, or merged without owner smoke | Retain exact delivery and acceptance states; do not mark the task accepted before its stated gates. |
| Model limit or safeguard refusal interrupts work | Preserve checkout/checkpoint and remaining task; continue through the authorized reviewed resume path. |
| Shared template receives an update | Review an upgrade against the project's adopted version and local extensions. No automatic policy replacement. |

These are document-level checks by the author. They are not an independent agent bootstrap, a second-project pilot, or product runtime evidence. `IMP-001` in the evolution record retains that pilot as the next validation step.
